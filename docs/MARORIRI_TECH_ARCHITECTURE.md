# MARORIRI 技術構成資料

`docs/MARORIRI_SITE_SPEC.md`ほか、既存の仕様書・ワイヤーフレーム・デザインガイドの内容と矛盾しないよう作成しています。今回は調査と提案のみで、Astroプロジェクトの作成、`package.json`の作成・変更、既存ファイルの修正・移動・削除、バックアップ作成、仕様書・ワイヤーフレームの確定内容の変更は一切行っていません。

## 1. 技術構成資料の目的

デザイン・実装に進む前に、現在のサイトが静的HTML・CSS・JavaScriptで構成されていることを踏まえ、MARORIRIサイト刷新に適した技術構成を検討する。既存サイトの構造を読み取り専用で調査し、「現状維持」と「Astro移行」の2案を比較したうえで、推奨構成・移行手順・リスクを整理する。

**⚠️ 重要な前提**: 調査の結果、現在のサイトは`k-snapstep.com`という実際に公開中のドメインで運用されており、Googleタグマネージャー(実データ計測)と外部フォームサービス(実際の問い合わせ受付)が稼働している。**これは検証用のサンドボックスではなく、稼働中の本番サイトである**という前提で、以降のリスク評価(14番)を行う。

## 9. 推奨する構成

**Astroへの移行を推奨する。**

理由:

- MARORIRIは固定7ページに加えて、**継続的に増えていく読みもの(2シリーズ+一覧+記事詳細)を持つ**サイトである。静的HTML案では、記事が増えるたびに一覧ページ・関連記事欄を手作業で更新する必要があり、後述のリスク(14番)のとおり更新漏れが発生しやすい。
- 読みものの記事データ項目(`MARORIRI_CONTENT_WIREFRAME.md`12番)は、すでに`title`・`series`・`publishedDate`等、スキーマ化を前提とした設計になっている。Astroの Content Collections は、この設計と直接対応する。
- 現在のCSS変数(トークン)による設計は、Astroのコンポーネント設計と相性がよく、大部分の考え方を引き継げる(4番)。
- Claude Codeでの継続的な更新(このプロジェクトのようにドキュメントベースで段階的に進める運用)において、スキーマ・コンポーネントで整合性が保たれる方が、後工程の作業も安全に進めやすい。

ただし、現在のホスティング・デプロイ方法が確認できていない(2番)ため、**Astro(静的サイト生成)への移行がホスティング環境と適合するかどうかは、次の段階で確認が必要**な前提条件として残る。

## 12. 既存URLとSEO

現在確認できるURLは、`/`(トップ)・`/labo/`・`/privacy.html`の3つ(ファイル構成からの推測。実際に検索エンジンにインデックスされているURLの全量は、Search Console等を確認しないと分からないため、確認できない範囲は断定しない)。

| 項目 | 提案 |
|---|---|
| 維持すべきURL | ドメイン`k-snapstep.com`自体は維持する前提とする。トップ(`/`)は維持しやすい |
| 変更が必要になりそうなURL | `/labo/`は「1日WEB担当者」に相当するページだが、旧LPと新しい「1日WEB担当者」ページは内容が異なるため、URLを維持するか新設するかは11番の作業と合わせて判断が必要 |
| 301リダイレクトが必要な可能性 | `/labo/`のURLを変更する場合、新しいURLへの301リダイレクトを設定する。読みもの記事をnoteから移行する場合も、旧note記事URLから新URLへのリダイレクト、またはnote側に移行案内を出す対応(`MARORIRI_CONTENT_WIREFRAME.md`15番)が必要になる可能性がある |
| title・descriptionの引き継ぎ方法 | 現在の`<title>`・`<meta description>`は旧ブランド名義のため、そのまま引き継がず、MARORIRIの確定本文(仕様書15番)をもとに新規作成する |
| 検索エンジンへの配慮 | URLを変更する場合は、公開前に301リダイレクトとsitemap.xmlを同時に用意し、変更を検索エンジンへ早期に伝える。ページ内容が刷新されること自体は避けられないため、「大きな変更」を完全に防ぐことはできないが、URLの不用意な変更を最小限にすることでインデックスの混乱を減らせる |
| sitemap.xmlの切り替え | 新しいsitemap.xmlを本番切り替え(11番の12)と同時に公開し、Search Consoleへ再送信する |
| 公開後にSearch Consoleで確認すること | クロールエラーの有無、旧URLの404発生状況、新ページのインデックス状況、GTM経由の計測が正しく発火しているか |

現在の公開URLの全量・検索順位・流入状況は、Search Console等の外部データを確認しないと分からないため、この資料の範囲では確認できないものとして扱う。

## 13. ロゴ・ブランド素材の扱い

現在確認できるロゴ(`logo-dark.png`・`logo-light.png`・`logo-symbol.png`)は、すべて旧ブランド「本来面目らぼ」の名称と、植物の根・芽を描いた線画マークで構成されている。MARORIRIの新しいロゴは、プロジェクト内には存在しない。

**比較**

| 案 | 内容 | 評価 |
|---|---|---|
| 案1 | 既存の旧ロゴをMARORIRI用に修正する | 旧ロゴは名称もモチーフ(植物・根)も新ブランドの方向性(避けるべき印象:「スピリチュアルサービス」)と一致しないため、修正よりも作り直しに近い作業になる可能性が高い |
| 案2 | MARORIRIの新しいロゴを作る | 新ブランドの印象(落ち着き・実務・判断力)に合わせて一から設計できるが、正式なロゴ制作には相応の検討時間がかかる |
| 案3 | 「MARORIRI」の文字だけのワードマークで進め、正式ロゴは後から差し替える | サイト公開のスケジュールを止めずに進められる。後からロゴ画像だけを差し替えれば済む設計にしておけば、影響範囲を限定できる |

**仮の推奨案**: 案3。ワードマーク(文字のみ)であれば、10番のディレクトリ構成・コンポーネント設計を進めながら並行してロゴ検討ができ、デザイン・実装のスケジュールを止めない。

**申し添え**: 調査の過程で、既存サイトから`@MaroRiri_k`という既存Xアカウントが見つかった。「マロリリ」という名称がこのアカウントに由来する可能性があり、**プロジェクト外(このXアカウント等)に、すでに使われている非公式なロゴ・アイコン相当の画像が存在する可能性がある**。旧ロゴの植物・根のマークをそのまま新ブランドに使う前提にはしないが、「新規作成が必須」とも断定せず、まずはこのアカウント等に既存素材がないかをユーザーに確認することを推奨する。
